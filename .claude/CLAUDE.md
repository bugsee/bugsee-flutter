# CLAUDE.md

Guidance for reviewers and agents working in this repository.

## Project

Bugsee Flutter wrapper for the 7.x native SDKs (Android and iOS). It is a rewrite in
progress; `PLAN.md` is the source of intent. The authoritative wrapper spec is
`sdk/wrapper-workbook` in the `bugsee/specs` repository (refer to it by repo name).

## Rules to enforce

- `native-versions.json` is the single source for every native pin. Each place that must
  repeat a value is compared to it by `test/native_versions_test.dart`. Do not hardcode
  a version elsewhere; update the guard when CI content changes.
- iOS is SwiftPM-only. There is deliberately no podspec (Bugsee publishes no pod). CI
  runs on macOS so SwiftPM can be enabled. Do not add a podspec.
- Flutter floor is 3.41.0 / Dart 3.11 (SwiftPM-only plugin fails `pub get` on Linux/Windows earlier; measured, see PLAN.md D5).
- Android builds need JDK 17 or 21. JDK 25 breaks the Gradle version in use.
- The Android initialization provider must never be named `Bugsee*InitProvider`.
- The wrapper type (`flutter`, the backend's identifier) and version (pubspec `version:`) are repeated in Dart, Android and iOS because native registers before Dart exists; `test/wrapper_identity_test.dart` compares every copy. Bump the iOS `BGSFlutterWrapper.m` and Dart `wrapper_identity.dart` with pubspec.
- The Dart <-> native bridge is Pigeon-generated (`pigeons/bridge.dart`; Dart, Java, Swift outputs committed, pin in `native-versions.json`). Never hand-edit `*.g.dart`, `Messages.java`, `Messages.g.swift`; run `dart scripts/generate_pigeon.dart` (CI checks with `--check`). Nothing in the bridge is exported from `lib/bugsee_flutter.dart` (a drift guard bans `bridge`/`messages` there); the public `Bugsee` facade (`lib/src/bugsee.dart`, behaviour in `lib/src/bugsee_runtime.dart`) is built on it.
- Lifecycle events: native strips the `com.bugsee.lifecycle.` prefix once, forwards unknown names unchanged, hops to the platform thread before touching Flutter, fans out to every attached engine, buffers (cap 64, drops oldest, drop log rate-limited) only while none is attached, and replays the latest status event to each new receiver. Events in flight to a detached receiver go back to the FRONT of the buffer. Status derives from Launching/Launched/Stopping/Stopped only; never take over the app's delegate/listener. The report-id event set, prefix and cap are repeated in Dart/Java/ObjC and compared by `test/lifecycle_drift_test.dart`.
- The wrapper object is replaced when Dart refines the identity, so state that must survive (secure rectangles, lifecycle hub) lives outside it (`SecureRectangleStore`, `LifecycleHub`, ObjC equivalents). Do not move it into the wrapper.
- iOS Objective-C wrapper tests: `ios/wrapper_tests` (symlinked sources), `xcodebuild test`. Android: JUnit under `android/src/test`.
- Secure rectangles (workbook Part 5; Dart `lib/src/secure`, `SecureRectangleStore` / `BGSFlutterSecureRectangleStore`): Dart publishes Flutter LOGICAL pixels per view WITH the device pixel ratio it measured them at, whole state, ordered by `(epoch, sequence)` where the epoch is a RANDOM id (never a clock): a new epoch is a new isolate and wins, a retired one is a dead isolate's straggler and is ignored. The SDKs' units differ and are read from SDK source: Android 7.4.2 takes PHYSICAL PIXELS in `View.getLocationOnScreen` space (factor = the message's ratio, which must equal the density of the Flutter view's `Resources` read at every pull), iOS 7.0.0-beta7 takes POINTS in the screen's coordinate space (factor = ratio / `UIScreen.scale` = 1; NEVER multiply by `UIScreen.scale`). A ratio that does not match the display now (density changed natively before Dart laid out again) covers the whole display until Dart republishes. Scale (including the view's own on-screen scale from its and its ancestors' transforms), then add the view's screen position, THEN floor l/t and ceil r/b. Versions are derived from what is served (per display, never 0, no-op never moves them); a display that never had a rectangle serves `[0, 0]`. Anything unplaceable, non-finite, mis-scaled, rotated/skewed or without an activity/view controller serves the WHOLE display (fail closed); only a view known to be off screen (iOS: in no window) serves nothing. A grace window (`GRACE_MS` = 0.12 s, in both stores, compared by the drift guard) serves each past set for that long AFTER IT stopped being current (not from the last change, so a long movement does not widen the cover to its path), so a moving region leaves no strip; the union shrinking back is itself a version change. Dart reports regions unclipped, including what their descendants paint outside the box, and drops one ONLY on positive evidence that it is not on screen (an ancestor that does not paint it, an IndexedStack showing another child, a clipping viewport it and what it paints lie wholly outside of). A disabled TickerMode is NOT evidence (it only stops animations). A detached layer is NOT such evidence (SnapshotWidget, the Zoom page transition). Every one of these rules has a test that fails when it is broken; keep it that way.
- Secure rectangle limits (known, documented, not bugs): a region that has just APPEARED is recorded in the clear for its first frame or so (it has no previous place to union with, and Dart cannot publish before layout has placed it; publishing from the build phase would only publish a guess); a rotated region is its bounding box; a region partly clipped is reported whole, so it can cover a few neighbouring pixels the clip hid; pixels drawn outside the region's subtree (an Overlay magnifier or tooltip) are not known to Flutter and not covered; FP noise can add one pixel to an edge; only the implicit view (id 0) is placed on mobile; a hot-restarted isolate that has no regions publishes nothing, so the old isolate's rectangles stay served until the engine detaches (debug only, over-covers); a region with more than 2000 descendants is not dropped by the viewport test (over-covers); iOS is verified in portrait only.

- Report handlers (workbook Part 7; `ReportHandlerPipeline.java`, `BGSFlutterReportHandlerPipeline.m`, Dart `lib/src/report` + `BugseeBridge.setReportHandlers`): the SDK completion runs exactly once on every path and the pipeline NEVER blocks (iOS calls the handler on the main thread and Dart's reply needs it: a wait is a deadlock; `test/report_handlers_drift_test.dart` greps for blocking primitives and for `isTerminating` being decided before anything touches Dart, time or the report). Terminating, no registered phase, no attached Dart, or a path the SDK does not wait on: complete at once. The window is the SDK's budget less a margin of a third (at most 10 s): 20 s live of the SDK's 30 s, iOS recovery 2 s of 3 s; the SDK's numbers are EXTRACTED from SDK source into `test/fixtures/report_enums.json` (`scripts/extract_report_enums.dart`, with the iOS source ref) and compared with the wrapper's by the drift guard, never wrapper against wrapper. The SDK starts its timer when it QUEUES the handler and ours starts at entry: that wait is not observable, only the margin absorbs it (an edit after the SDK moved on can still be accepted: documented limit); the observable hop to the platform thread is deducted (`deadlineMs` sent to Dart is what is left; an over window is completed, not offered). An edit holds the per-handle lock across check-and-apply and `done` flips under it, the SDK completion/Dart/scheduler are called outside it. `resetReportHandlers` (called first by `start()`) completes a previous isolate's outstanding deliveries. The drift guard bans blocking primitives in every file of the report path and allow-lists each `synchronized`. The path is told apart by thread for the time budget only; never pass it to Dart, never infer a recovered crash (7.2.3). The proxy is live until the completion runs; native answers `false` to a late edit and Dart throws `ReportClosedError`. `onBefore` at-most-once, `onAfter` at-least-once: Dart dedupes on the stable `deliveryId`. Enums cross by value; the Pigeon bridge declares NO enum (Pigeon sends ordinals); `test/fixtures/report_enums.json` is extracted from both SDKs by `scripts/extract_report_enums.dart` (re-run when a native pin moves: the parity test fails on stale pins) and compared with Dart/Java/ObjC, and the JUnit/XCTest compare it to the real SDK enums. Attachments are Phase 6 (path-first).
- Options and launch (workbook Part 8; Phase 4a). The two SDKs PUBLISH an immutable options manifest per release (bugsee/specs `sdk/options`, generated from their live registry, so complete: extension modules, null defaults, hidden keys); both are vendored verbatim in `test/fixtures/option_manifests/{android,ios}.json` (`scripts/sync_option_manifests.dart`, `--check` refetches, weekly in `native-pins.yml`; the pins are in `native-versions.json` `optionsManifest`). `scripts/verify_option_manifests.dart` is an independent read of SDK SOURCE (keys, hidden keys, enum values; needs the private SDK checkouts, so local only, last result in PLAN.md). `scripts/extract_option_docs.dart` extracts the SDKs' own prose into `docs.json` (also local; a few options have no prose in source and carry a labelled `wrapper` description). `scripts/generate_options.dart` writes `lib/src/options/option_registry.g.dart` and `bugsee_options.g.dart` (the typed `BugseeOptions`, its enums) from those three; `--check` runs offline in CI (`options-codegen` job). Never hand-edit the `.g.dart`. A new SDK enum, a type that differs between platforms, or one value with two names fails the generator on purpose: decide, then record it (`enumFamilies`, `knownNameDivergences`, and the test lists in `test/option_manifests_test.dart`). Field name = key (`capture.video.frame-rate` -> `captureVideoFrameRate`). `test/option_manifests_test.dart`: STRICT on keys, types and enum values across platforms, default differences listed explicitly (a new one fails until reviewed); one-sided enum members (`FrameRate.raw`, Android only) listed explicitly.
- Option encoding (`lib/src/options/launch_options.dart`): ONE flat `com.bugsee.option.*` map goes to both platforms, nothing is renamed per platform. Enums cross as the SDK INTERNAL integer. A key or enum constant the other platform lacks is SKIPPED with a debug warning (a shared configuration may set platform options); a key neither SDK registers, a hidden key, a wrong type, a value neither SDK has, a typed+custom duplicate or a bad endpoint is an `ArgumentError` BEFORE native is touched (both SDKs drop all of these silently). The one platform-specific step is natively Android: its map path takes an enum as the constant or its NAME and DROPS a number, so `LaunchOptionValues.java` turns the integer into the constant through the enum's own factory (never `values()[n]`); its table is compared with the manifest by JUnit (by value, against the real SDK enums) and by `test/launch_drift_test.dart`. iOS takes the numbers as they are (XCTest against the real SDK). Bundled modules (`bugsee-android`, `-ndk`; iOS `Bugsee`) get typed fields; the leak module's four options do not (repeated in the generator and `launch_options.dart`, compared with `android/build.gradle`).
- Endpoint (workbook 8.2 is stale for the pinned SDKs): iOS 7.0.0-beta7 registers the SAME hidden `com.bugsee.option.$$ENDPOINT` (manifest, nextgen d33dcc987) and strips trailing `/v2` itself, like Android; the flat `endpoint` is only a legacy alias. So one version-less value under the one namespaced key goes to both (`lib/src/options/endpoint.dart`, the only place; runtime-verified on both). If an SDK diverges again, change only that file. `BugseeOptions.endpoint` is the one supported hidden-key override; the SDKs strip hidden options from uploaded `sdk.options` (8.4), the wrapper never sends `$$WRAPPER`/`$$DEBUG`.
- Launch (`LaunchOps.java`, `BGSFlutterLaunchOps.m`, `lib/src/bugsee_runtime.dart`): the SDK is behind a seam in both natives so decisions are unit-tested. STATUS IS READ FIRST: Android auto-init (manifest `com.bugsee.app-token`, unless `com.bugsee.auto-init` is false) and a second launch make `Bugsee.launch` early-return "success" and DROP the options with only a log line, indistinguishable by its callback, so Launching/Launched is answered `already-running` without calling the SDK; Stopping is refused (the SDK refuses too); iOS: `started:` YES with the SDK still Stopped is a launch the SDK deferred (app in background). Dart attaches the bridge and refines the wrapper identity BEFORE the SDK launches (Part 2). Status crosses by NAME, outcomes as strings (no Pigeon enum), vocabulary compared across Dart/Java/ObjC by `test/launch_drift_test.dart`. An SDK exception crosses as `launch-failed` (never the token or options in the message). `getLaunchOptions` (merged over defaults) is the same on both SDKs at the pins; `getHostLaunchOptions` is NOT (Android: everything the app passed; iOS: only what differs from the iOS default, `BGSBugseeEnvironment hostLaunchOptions`): documented, not normalised.
- Android unit tests cannot build the SDK's option container (its registry needs an Android runtime), so the SDK's real handling of the translated map is shown on a device: `example/integration_test/launch_test.dart` (run it on an emulator AND a simulator; both pass).
- Report handler limits (known, not bugs): an edit not awaited before the handler returns is lost and throws; a re-delivery of the same report and phase in the same isolate is not re-run (a first run whose edits were lost is not retried in-process); several engines: the most recently attached one with a handler gets the delivery; a Dart handler cannot run for an iOS recovery that happens before the engine exists (completed at once); Android early-crash recovery never reaches Dart.

## Checks

```bash
flutter analyze && flutter test
dart scripts/extract_report_enums.dart --check ...   # see the script header; inputs are SDK source files
(cd example && flutter build apk --debug)        # JDK 17 or 21
(cd example && flutter build ios --debug --no-codesign)
dart scripts/generate_pigeon.dart --check          # bridge outputs current
dart scripts/generate_options.dart --check         # option registry + BugseeOptions current (offline)
dart scripts/sync_option_manifests.dart --check    # network: the vendored manifests are the SDKs' published ones
dart scripts/verify_option_manifests.dart --android-repo ... --android-ref v7.4.2 --ios-repo ... --ios-ref origin/nextgen  # local: against SDK source
(cd example && flutter test integration_test/launch_test.dart -d <emulator or simulator>)
(cd example/android && ./gradlew :bugsee_flutter:testDebugUnitTest)
(cd ios/wrapper_tests && xcodebuild test -scheme bugsee_flutter_wrapper_tests -destination 'platform=iOS Simulator,name=<iPhone>')
```
