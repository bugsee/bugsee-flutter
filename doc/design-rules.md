# Design rules in full

The detailed rules behind `.claude/CLAUDE.md` (the short reviewer guide): each section is an area of the plugin, with the invariants the code
must keep, the reasons, the known limits, and the tests or drift guards that hold them. A rule that has a guard fails CI when it is broken;
keep it that way when you change the code (change the guard in the same PR, with the reason). Where a page of its own exists
(`api-surface.md`, `network.md`, `logs.md`, `exceptions.md`, `attachments.md`, `view-hierarchy.md`, `verification.md`, `architecture.md`) it has the data flow and
the evidence; this page is the checklist.

## Secure rectangles

Secure rectangles (workbook Part 5; Dart `lib/src/secure`, `SecureRectangleStore` / `BGSFlutterSecureRectangleStore`): Dart publishes Flutter LOGICAL pixels per view WITH the device pixel ratio it measured them at, whole state, ordered by `(epoch, sequence)` where the epoch is a RANDOM id (never a clock): a new epoch is a new isolate and wins, a retired one is a dead isolate's straggler and is ignored. The SDKs' units differ and are read from SDK source: Android 7.4.2 takes PHYSICAL PIXELS in `View.getLocationOnScreen` space (factor = the message's ratio, which must equal the density of the Flutter view's `Resources` read at every pull), iOS 7.0.0-beta7 takes POINTS in the screen's coordinate space (factor = ratio / `UIScreen.scale` = 1; NEVER multiply by `UIScreen.scale`). A ratio that does not match the display now (density changed natively before Dart laid out again) covers the whole display until Dart republishes. Scale (including the view's own on-screen scale from its and its ancestors' transforms), then add the view's screen position, THEN floor l/t and ceil r/b. Versions are derived from what is served (per display, never 0, no-op never moves them); a display that never had a rectangle serves `[0, 0]`. Anything unplaceable, non-finite, mis-scaled, rotated/skewed or without an activity/view controller serves the WHOLE display (fail closed); only a view known to be off-screen (iOS: in no window) serves nothing. A grace window (`GRACE_MS` = 0.12 s, in both stores, compared by the drift guard) serves each past set for that long AFTER IT stopped being current (not from the last change, so a long movement does not widen the cover to its path), so a moving region leaves no strip; the union shrinking back is itself a version change. Dart reports regions unclipped, including what their descendants paint outside the box, and drops one ONLY on positive evidence that it is not on screen (an ancestor that does not paint it, an IndexedStack showing another child, a clipping viewport it and what it paints lie wholly outside). A disabled TickerMode is NOT evidence (it only stops animations). A detached layer is NOT such evidence (SnapshotWidget, the Zoom page transition). Android: a pull asks the main thread to re-read the placements (throttled to 100 ms) and answers from the last completed read, so a view that moved with no relayout is served at its old place for up to about one pull; a refresh asked for and not completed for `REFRESH_STALE_MS` (1 s: a stuck main thread) covers every placed view whole until one completes (tracked from the OLDEST unanswered request, so throttle suppression cannot hide it, and independent of the pull rate; marking every pull as pending would blank the display on every pull). iOS refreshes synchronously on the main thread, where the SDK pulls today. A failed publish is retried by a timer with deterministic backoff (1 s doubling to a 30 s cap) and NEVER abandoned (native keeps the last accepted state, so giving up leaves a stale mask and a new region in the clear); frames never resend the state that just failed, and once `maxRetries` consecutive failures passed a CHANGED state (the only kind that can add a region) goes out once `retryDelay` has passed since the last attempt, never per frame (no flood; a missing plugin costs one message per 30 s while nothing moves, at most one per second while regions move). The registry's clock is injectable for tests. Every one of these rules has a test that fails when it is broken; keep it that way.

## Secure rectangle limits

Secure rectangle limits (known, documented, not bugs): a region that has just APPEARED is recorded in the clear for its first frame or so (it has no previous place to union with, and Dart cannot publish before layout has placed it; publishing from the build phase would only publish a guess); a rotated region is its bounding box; a region partly clipped is reported whole, so it can cover a few neighbouring pixels the clip hid; pixels drawn outside the region's subtree (an Overlay magnifier or tooltip) are not known to Flutter and not covered; FP noise can add one pixel to an edge; only the implicit view (id 0) is placed on mobile; a hot-restarted isolate that has no regions publishes nothing, so the old isolate's rectangles stay served until the engine detaches (debug only, over-covers); a region with more than 2000 descendants is not dropped by the viewport test (over-covers); iOS is verified in portrait only.

## Report handlers

Report handlers (workbook Part 7; `ReportHandlerPipeline.java`, `BGSFlutterReportHandlerPipeline.m`, Dart `lib/src/report` + `BugseeBridge.setReportHandlers`): the SDK completion runs exactly once on every path and the pipeline NEVER blocks (iOS calls the handler on the main thread and Dart's reply needs it: a wait is a deadlock; `test/report_handlers_drift_test.dart` greps for blocking primitives and for `isTerminating` being decided before anything touches Dart, time or the report). Terminating, no registered phase, no attached Dart, or a path the SDK does not wait on: complete at once. The window is the SDK's budget less a margin of a third (at most 10 s): 20 s live of the SDK's 30 s, iOS recovery 2 s of 3 s; the SDK's numbers are EXTRACTED from SDK source into `test/fixtures/report_enums.json` (`scripts/extract_report_enums.dart`, with the iOS source ref) and compared with the wrapper's by the drift guard, never wrapper against wrapper. The SDK starts its timer when it QUEUES the handler and ours starts at entry: that wait is not observable, only the margin absorbs it (an edit after the SDK moved on can still be accepted: documented limit); the observable hop to the platform thread is deducted (`deadlineMs` sent to Dart is what is left; an over window is completed, not offered). An edit holds the per-handle lock across check-and-apply and `done` flips under it, the SDK completion/Dart/scheduler are called outside it. `resetReportHandlers` (called first by `start()`) completes a previous isolate's outstanding deliveries. The drift guard bans blocking primitives in every file of the report path and allow-lists each `synchronized`. The path is told apart by thread for the time budget only; never pass it to Dart, never infer a recovered crash (7.2.3). The proxy is live until the completion runs; native answers `false` to a late edit and Dart throws `ReportClosedError`. `onBefore` at-most-once, `onAfter` at-least-once: Dart dedupes on the stable `deliveryId`. Enums cross by value; the Pigeon bridge declares NO enum (Pigeon sends ordinals); `test/fixtures/report_enums.json` is extracted from both SDKs by `scripts/extract_report_enums.dart` (re-run when a native pin moves: the parity test fails on stale pins) and compared with Dart/Java/ObjC, and the JUnit/XCTest compare it to the real SDK enums. Attachments and screenshots are path-first (see "Report files").

## Managed view hierarchy (`vh`)

Managed view hierarchy (`vh`, workbook Part 6; Dart `lib/src/view_hierarchy`, `ViewHierarchyStore.java` / `BGSFlutterViewHierarchyStore`; design, payload, privacy, limits in `doc/view-hierarchy.md`): the SDK asks `requestData("vh")` on the MAIN thread and times 500 ms from when the call returns, so the wrapper answers SYNCHRONOUSLY from a native cache Dart keeps current; NEVER make that answer wait for Dart or post it (a wait is a deadlock; a late reply misses the report when the snapshot is made on the main thread, which bugsee-android PR #120, in 7.4.2, does not cover; iOS does not even ask on the main thread). The cache stores a JSON TEMPLATE (text cut at the snapshot's age and at every node's box) plus the boxes in the view's logical pixels; the stores convert boxes per answer with `SecureRectangleStore.Mapper` / `BGSFlutterPlacementMapper`, the ONE place the ratio, unit (Android physical pixels, iOS points), view scale and position are combined (the secure rectangles use the same object; a drift test keeps the arithmetic out of every other file), and answer `null` when anything is unplaceable, off screen, mis-scaled, non-finite, malformed or stuck. Never parse the JSON natively. PRIVACY IS OURS (the SDK stores the string unread): the builder (`hierarchy_builder.dart`) takes only `runtimeType` names and structure from the element/render tree: never text, controllers, semantics, `Key`s (a `ValueKey<String>` is arbitrary app data; the spec's own example leaks one), tags, route names, `toString()` of a widget; a `BugseeSecureView` subtree is ONE node with a fixed name, its secure-rectangle box and `secure: true`, nothing below it; `id` is a counter; any error returns `null` and sends nothing. `test/view_hierarchy_drift_test.dart` allow-lists what may be read off a render object and bans the text channels by pattern: a new read must be reviewed for text. Publishing needs the SDK launched AND its `capture.view-hierarchy` option on AND the app in the foreground (`controller.dart`); the publisher builds only in a post-frame callback or a timer (never inside a frame), schedules no frames of its own, spaces builds by 20x their cost (min 300 ms, max 5 s), sends only changes, and caps the walk (12 ms, 2000 nodes, 256 KiB, 512 levels: cut and marked `truncated`, never partial JSON). A detached engine drops its snapshot (serves nothing). The age is native's (`options.age_ms`, computed per answer) because the SDK stamps the entry with the reply time; there is deliberately no maximum age (Flutter draws only on a frame). The SDK facts (type, 500 ms, 50 ms iOS backoff, the main-thread-only wait) are extracted from SDK source into `test/fixtures/data_requests.json` (`scripts/extract_data_requests.dart`; re-run when a pin moves). Public: `Bugsee.captureViewHierarchy()` (flushes, then asks the SDK). Limits: only the implicit view; a Flutter view off the screen origin is covered by JUnit/XCTest, not a device; iOS bundles are not verifiable on a simulator with a placeholder token (the device test reads the capture buffer).

## Options and the manifests

Options (workbook Part 8). The two SDKs PUBLISH an immutable options manifest per release (bugsee/specs `sdk/options`, generated from their live registry, so complete: extension modules, null defaults, hidden keys); both are vendored verbatim in `test/fixtures/option_manifests/{android,ios}.json` (`scripts/sync_option_manifests.dart`, `--check` refetches, weekly in `native-pins.yml`; the pins are in `native-versions.json` `optionsManifest`). `scripts/verify_option_manifests.dart` is an independent read of SDK SOURCE (keys, hidden keys, enum values; needs the private SDK checkouts, so local only, last result in PLAN.md). `scripts/extract_option_docs.dart` extracts the SDKs' own prose into `docs.json` (also local; a few options have no prose in source and carry a labelled `wrapper` description). `scripts/generate_options.dart` writes `lib/src/options/option_registry.g.dart` and `bugsee_options.g.dart` (the typed `BugseeOptions`, its enums) from those three; `--check` runs offline in CI (`options-codegen` job). Never hand-edit the `.g.dart`. A new SDK enum, a type that differs between platforms, or one value with two names fails the generator on purpose: decide, then record it (`enumFamilies`, `knownNameDivergences`, and the test lists in `test/option_manifests_test.dart`). Field name = key (`capture.video.frame-rate` -> `captureVideoFrameRate`). `test/option_manifests_test.dart`: STRICT on keys, types and enum values across platforms, default differences listed explicitly (a new one fails until reviewed); one-sided enum members (`FrameRate.raw`, Android only) listed explicitly.

## Option encoding

Option encoding (`lib/src/options/launch_options.dart`): ONE flat `com.bugsee.option.*` map goes to both platforms, nothing is renamed per platform. Enums cross as the SDK INTERNAL integer. A key or enum constant the other platform lacks is SKIPPED with a debug warning (a shared configuration may set platform options); a key neither SDK registers, a hidden key, a wrong type, a value neither SDK has, a typed+custom duplicate or a bad endpoint is an `ArgumentError` BEFORE native is touched (both SDKs drop all of these silently). The one platform-specific step is natively Android: its map path takes an enum as the constant or its NAME and DROPS a number, so `LaunchOptionValues.java` turns the integer into the constant through the enum's own factory (never `values()[n]`); its table is compared with the manifest by JUnit (by value, against the real SDK enums) and by `test/launch_drift_test.dart`. iOS takes the numbers as they are (XCTest against the real SDK). Bundled modules (`bugsee-android`, `-ndk`; iOS `Bugsee`) get typed fields; the leak module's four options and deprecated options (one at the pins) do not (`custom` reaches them, with a warning for a deprecated one; a custom enum NAME is mapped to its number by the manifest, since iOS KVC would read a string as 0) (repeated in the generator and `launch_options.dart`, compared with `android/build.gradle`).

## Endpoint

Endpoint (workbook 8.2 is stale for the pinned SDKs): iOS 7.0.0-beta7 registers the SAME hidden `com.bugsee.option.$$ENDPOINT` (manifest, nextgen d33dcc987) and strips trailing `/v2` itself, like Android; the flat `endpoint` is only a legacy alias. So one version-less value under the one namespaced key goes to both (`lib/src/options/endpoint.dart`, the only place; the wrapper's encoding is covered by tests; the launch integration test does NOT assert endpoint handling at runtime, so the SDKs' reading of it is as read from their manifests and source, not shown on a device). If an SDK diverges again, change only that file. `BugseeOptions.endpoint` is the one supported hidden-key override; the SDKs strip hidden options from uploaded `sdk.options` (8.4), the wrapper never sends `$$WRAPPER`/`$$DEBUG`.

## Launch

Launch (`LaunchOps.java`, `BGSFlutterLaunchOps.m`, `lib/src/bugsee_runtime.dart`): the SDK is behind a seam in both natives so decisions are unit-tested. A stop is marked on iOS BEFORE the hop to the main queue (`beginStop`; the SDK sets Stopping a hop later, so a launch after an unawaited stop would read `launched`); Android sets STOPPING synchronously. STATUS IS READ FIRST: Android auto-init (manifest `com.bugsee.app-token`, unless `com.bugsee.auto-init` is false) and a second launch make `Bugsee.launch` early-return "success" and DROP the options with only a log line, indistinguishable by its callback, so Launching/Launched is answered `already-running` without calling the SDK; Stopping is refused (the SDK refuses too); iOS: `started:` YES with the SDK still Stopped is a launch the SDK deferred (app in background). Dart attaches the bridge and refines the wrapper identity BEFORE the SDK launches (Part 2). Status crosses by NAME, outcomes as strings (no Pigeon enum), vocabulary compared across Dart/Java/ObjC by `test/launch_drift_test.dart`. An SDK exception crosses as `launch-failed` (never the token or options in the message). `getLaunchOptions` (merged over defaults) is the same on both SDKs at the pins; `getHostLaunchOptions` is NOT (Android: everything the app passed; iOS: only what differs from the iOS default, `BGSBugseeEnvironment hostLaunchOptions`): documented, not normalised. The SDK's launch callback is answered to Dart ONCE (an `AtomicBoolean` / a locked flag around it; tested with a fake that calls back twice and one that calls back then throws), because a second reply is "Reply already submitted" on Android and a double continuation resume on iOS. NOT verified on the real iOS SDK: that `[Bugsee stop:]` always calls its completion (a stop before any launch, or during `launching`); if it did not, `gStopsInFlight` would stay above zero and every later launch would be refused as `stopping`.

## Android unit tests and the launch integration test

Android unit tests cannot build the SDK's option container (its registry needs an Android runtime), so the SDK's real handling of the translated map is shown on a device: `example/integration_test/launch_test.dart` (run it on an emulator AND a simulator; both pass).

## Report handler limits

Report handler limits (known, not bugs): an edit not awaited before the handler returns is lost and throws; a re-delivery of the same report and phase in the same isolate is not re-run (the id is recorded BEFORE the handler runs, so a handler that threw or overran counts as delivered and is not retried in-process: the SDK's own redelivery after a crash is the retry, in a later process; decided, not an oversight); several engines: the most recently attached one with a handler gets the delivery; a Dart handler cannot run for an iOS recovery that happens before the engine exists (completed at once); Android EARLY-crash recovery (a second crash before the first `onResume`: the `bugsee-report-handler-bounded` thread, completed at once) never reaches Dart; a native-crash report recovered after a normal session is NOT that path: measured on a device (`doc/verification.md`, scenario 3) it is dispatched on `BugseeReportHandlerThread` (not main, unlike the workbook's table) with `isTerminating` false and the live window, Dart runs and its attribute, label and file land in the recovered bundle. Handles (`rh-N`) are looked up by handle alone, with no owner check: the wrapper trusts every caller in the app's own process (same trust model as the SDK itself; stated in `attachments.md`).

## Public facade

Public facade (`lib/src/bugsee.dart` -> `BugseeRuntime`, native `FacadeOps.java` / `BGSFlutterFacadeOps.m`, inventory and per-method before-launch behaviour in `doc/api-surface.md`): every method crosses the Pigeon bridge as one call on the platform thread, with the SDK behind a seam in both natives (`FacadeOps.Sdk`, `BGSFlutterFacadeSDK`) so JUnit/XCTest see what reaches it. Dart validates first (`lib/src/facade/validation.dart`), native defends again, an SDK exception is caught natively (an `NSException` escaping into Swift crashes the app) and comes back as a failure code (`invalid-argument`, `attribute-rejected`, `sdk-error`, `not-attached`; repeated in Dart `FacadeWire`, Java and ObjC, compared by `test/facade_drift_test.dart`). Errors are `BugseeException` subclasses delivered through the `Future` (all facade methods are `async`; names/values in a message are never user data). The wrapper QUEUES AND GATES NOTHING before `launch`: each SDK does what it does (attributes, user id and blackout work; event/trace/log/breadcrumb/notify/upload/dialog are dropped); the table with source refs is in `doc/api-surface.md`: when an SDK's behaviour changes, change the table and the method docs together. An attribute the SDK dropped for size is only knowable by READING IT BACK (Android `setAttribute` is void, iOS answers YES): do not remove the read-back. iOS also DELETES the key it was overwriting on a total-size overflow, so the previous value is read first and written back on a rejection (Android checks first). `BugseeAttributeException` is deliberately not a `BugseeArgumentException` (`rejected` is the SDK's refusal). `addBreadcrumb` needs the SDK Launching/Launched natively (Android's factory consumer is cached after stop, iOS `+addBreadcrumb:` has no gate). Both Android attribute getters narrow a double to its persisted float. Every facade call attaches lazily (`_call` -> `ensureStarted`). Test hooks and bridge types are not on exported signatures: `debugSetBugseeRuntime` and `createReportProxy`/`closeReportProxy` are src-only functions, and `test/public_api_test.dart` pins the members of the exported classes too. The attribute/number limits (1024 UTF-16 units, `Float.MAX_VALUE`, 2^63) are repeated in Dart, Java and ObjC and compared by the drift guard. Enums: breadcrumb level crosses by NAME (the SDKs number it differently), log level and severity by the SDK integer; no Pigeon enum. No pause/resume/relaunch shim (`test/public_api_test.dart` bans them). On a platform with no SDK the facade is a no-op (neutral values, one debug warning) and only `launch` throws. `test/public_api_test.dart` PINS the exported symbols and `Bugsee`'s static members: adding API means editing that list in the same change; an exported file may not re-export. The public widget is `BugseeSecureView` (over the internal `BugseeSecureRegion`); `ReportProxy`/`ReportSnapshot`/`BugseeReportHandler`/`LifecycleEvent` are public, their constructors/bridge hooks are `@internal`. Not exposed on purpose (documented, with reasons): APM spans (handle registry + thread-local active span), appearance, relaunch, secure rectangles/activities, deleteCollectedData.

## Facade runtime verification

Facade runtime verification: `example/integration_test/facade_test.dart` (Android emulator AND iOS simulator): attribute/identity/blackout read back from the SDKs, the 1024/total attribute limits (they DIFFER: Android keeps a 1024-char string and ~42x600 chars, iOS rejects 1024 chars and takes ~40x600), a report handler around a real `Bugsee.upload` (before/after run, edits visible on the live report), breadcrumbs accepted only when launched with `captureBreadcrumbs`. iOS stops a placeholder token after the first refused upload, so the upload comes first in that test and repeated launch/stop cycles with it can be refused. The reports it leaves pending make iOS stop a LATER launch of the same install (`launch_test` then fails at `getStatus == launched`): `xcrun simctl uninstall <udid> com.bugsee.bugseeFlutterExample` between `facade_test` and `launch_test`.

## Network capture

Network capture (`lib/src/network`, native `NetworkOps.java` / `BGSFlutterNetworkOps.m`, doc `doc/network.md`): Dart's `dart:io` is invisible to the SDKs, so `Bugsee.installNetworkCapture()` puts a chaining `BugseeHttpOverrides` in front of `HttpOverrides.current` (the previous overrides MAKE the client and answer `findProxyFromEnvironment`; `CapturingHttpClient implements HttpClient` with NO `noSuchMethod`, so a member a newer SDK adds fails to compile instead of being silently unforwarded; a client already wrapped by another layer is not wrapped again) and records `before`/`redirect`/`complete`/`error`/`abort` entries. It must never change what the app sees or its timing (the differential test in `test/http_capture_test.dart` compares every observable with an unwrapped client), never throw into the app (every hook is try/catch), and never hold unbounded memory (`BodyTee`: copy only while text and within `capture.network.body-size-limit`, count beyond; a binary body is never copied). The SDK's body rules are mirrored from SDK source (Android `NetworkEventsProducer`/`applyBodyFilters`, iOS `BGSCaptureDataEntryNetwork`), request and response in the SDK's own order, and applied BEFORE copying. Events go `submit` (O(1)) -> bounded queue (512 events / 8 MiB, the NEW event is dropped and counted) -> Dart filter -> batches (<= 32 / 512 KiB, ONE in flight) -> `addNetworkEvents` on a serial BACKGROUND thread of the plugin (a Pigeon `@TaskQueue`, unlike the rest of the facade: the SDK's sanitizer and the app's native filter run on the calling thread, one body-size-limit's worth of text per event, and must not take UI time; the channel is documented as callable from any thread). The Dart filter is the privacy boundary and FAILS CLOSED (a throw, a wrong return type, a hang past its timeout drops the event; `id`/`stage`/`method`/`status`/`size` are the exchange's and a filter cannot change them). Injection uses the SDKs' WRAPPER CHANNEL, shipped at both pins (Android 7.4.2 `BugseeWrapperChannel`, iOS 7.0.0-beta7 `BGSWrapperChannel`; the wrapper-channel spec still says Proposed): `FlutterWrapper.onWrapperChannelAvailable` only STORES the channel in the process-wide `NetworkChannelHolder` / `BGSFlutterNetworkChannel` (the wrapper object is replaced when Dart refines the identity and the SDK retires the old channel then; store and return, nothing else, the SDK delivers it under its registration lock). Events are ALWAYS submitted with `requiresFiltering = true`: `false` would skip the SDK's default sanitizer and the app's native filter (`BugseeCaptureDataProviderNetwork.onNetworkEvent`, `BGSCaptureDataProviderNetwork.addNetworkEvent`); a Dart filter therefore does NOT replace the sanitizer and a native filter runs after it (double filtering is by design, documented). Network events carry NO source attribution at the pins (only `log` does): `mechanism: dart:io` is the label. Gate mirrored natively AND in Dart: only `launched` (Android would take `launching` into a 32-entry buffer, iOS drops it) and `capture.network` on; the policy is read from `getLaunchOptions` at install, after launch/stop and on every status event, a stop takes effect before the re-read, a failed read accepts nothing. iOS has no `createNetworkEvent` (the factory answers nil at the pin: build `BugseeNetworkEvent` directly), no redirect stage (the hop entries are not handed over; `redirectedFromURL` rides the final event), spells `abort` `cancel`, has no `statusText`/timings. The wire vocabulary (stages, reasons, max age, mechanism, filter timeout) is `test/fixtures/network_wire.json`, compared with Dart/Java/ObjC by `test/network_drift_test.dart` and with the REAL SDK enums/constants by `NetworkWireParityTest` and `BGSFlutterNetworkOpsTests`; the injection files may not wait, sleep or take a lock (guard in the drift test). The event age crosses as `ageMs` (Dart monotonic clock) and native subtracts it from the SDK's own clock (Android `currentTimestamp()`, which is not wall time once the clock was corrected). Requests to `bugsee.com` and below and to the configured `endpoint` host are never captured. URL hygiene (review round): userinfo is stripped in Dart from EVERY URL-bearing field (url, redirectedFrom, error texts, and once more after the filter) and URL-valued headers (`location`, `content-location`, `referer`, `refresh`) lose query values (`lib/src/network/url_redaction.dart`; the SDKs sanitize the url field only, Android breadcrumbs and error texts keep what they are given); redirect entries carry no headers; a manual `response.redirect()` starts a NEW exchange; `uninstall` still submits what was already captured; `ageMs` is stamped just before the batch is sent; `body-size-limit` is capped at 2 MiB; `install` refuses a zone that scopes its own overrides; `networkCaptureStats.submittedToSdk` is submitted, not recorded. Limits (documented, not bugs): other isolates, WebSocket frames (the handshake is an exchange), a client created before the install, an app that replaces the overrides without chaining (install again), a request never closed or a response never listened to. Runtime check: `example/integration_test/network_test.dart` (`--dart-define=BUGSEE_ENDPOINT=<mock API>`; `NET_HOLD=<s>` keeps the app alive to read the bundle with `adb run-as`).

## Log capture

Log capture (`lib/src/logs`, native `LogOps.java` + `BugseeLogSdk.java` / `BGSFlutterLogOps.m`, doc `doc/logs.md`): `print` is hooked by a ZONE specification (`Zone.root` cannot be replaced: `runWithLogCapture`, `runGuarded`, or the app's own `runZoned`), `debugPrint` by a chained global callback (one closure per install holding the callback it chains to; restored only when still ours), both record through `LogPipeline` (O(1) submit, rate limit 500/s burst 1000, 4000-unit line cap, queue 1000 lines / 2 MiB, Dart filter fail closed, batches of 64 on a background Pigeon queue). The original output ALWAYS happens first; the capture runs in `runSuppressed` zones where it must not record (filter, forwarded `debugPrint`). Lines go through the wrapper channel with source `Custom` ONLY (never `Bugsee`, which is the app's `Bugsee.log` and skips filters; reserved values are coerced by the SDKs anyway), tag Android only, level 1..5 the same on both SDKs, no timestamp (neither channel takes one). Gates mirrored in Dart AND native: launching|launched + `capture.logs` (+ `capture.logs.level`, which Android does not apply to channel lines). The SDKs have NO log sanitizer and their own console capture (Android logcat, source 3 tag `flutter`) can record the same print raw: the Dart filter does not cover it (doc). `FlutterError` dumps (`══╡`) and `bugsee_flutter: ` lines are never recorded. Do not rename `NetworkChannelHolder` (shared channel for network and logs) without the drift guards.

## Dart errors

Dart errors (`lib/src/exceptions`, `ExceptionOps.java` / `BGSFlutterExceptionOps.m`, full contract and measurements in `doc/exceptions.md`): the backend (worker `crash/managed`) routes on the literal `FlutterManagedException` (carrier class name on Android, `NSException` name on iOS, and `internalType` in the document) and reads the JSON document out of the reason: keys `internalType, name, reason, signature, frames, originalStackTrace` ONLY (the worker ignores anything else, and ignores `signature` too: both SDKs hash it). NEVER rename the carrier (`android/consumer-rules.pro` keeps it through R8); `test/exceptions_drift_test.dart` compares the name and limits across Dart/Java/ObjC and which SDK call each path makes. `originalStackTrace` is `stack.toString()` untouched for a non-symbolic (obfuscated / split-debug-info) stack: the build id and `#00` lines are what the backend symbolicates from; a symbolic one only has local `file://` paths reduced. Parse the printed text with `Chain.parse`, never `Chain.forTrace` (it links to the calling zone). Type names by `is` in specific-before-general order (a `FlutterError` IS an `AssertionError`, `RangeError` IS an `ArgumentError`), never `runtimeType` alone (obfuscated). The document MUST carry `signature` (`exceptionSignature`: type, first line of the reason without volatile parts, top 5 user frames; non-symbolic frames by `virt`+symbol): both SDKs hash it with a carrier name and Java stack that are the same for every Dart error, and the server matches issues on the SDK signature BEFORE the worker (one issue at its recording limit would drop every Dart error; 12004 blacklists on the device); `ExceptionSignatureTest` / `BGSFlutterExceptionSignatureTests` feed `signature_cases.json` to the SDKs' own signature code. Handled -> `Bugsee.logException` / iOS `logException:reason:domain:`; unhandled -> `Bugsee.logUnhandledException(Throwable, Map)` / iOS `logUnhandledException:reason:` (an unhandled one is a crash report that iOS delivers at the next launch). The bridge call is `@async`: Android runs the SDK call on `ExceptionDispatcher`'s single thread (bounded queue of 32, drops and counts; the SDK writes an unhandled report on the calling thread), iOS stays on the main queue. The wrapper gates both paths on Launching/Launched on both platforms (iOS's unhandled path is not gated by the SDK); nothing is queued. Public API: `logException(e, [stack])` (error), `logUnhandledException(e, [stack])` (crash), `reportException(e, {stackTrace, handled, domain})` (Dart cannot mix optional positional and named). The installed handlers (`ErrorCapture`) chain (FlutterError: ours first, then the previous; PlatformDispatcher: the previous FIRST, its answer `true` makes the report an error even with `reportAsCrash`, `false` without one, reported in a `finally`), restore only if still current (else inert pass-through), are idempotent, must be installed AFTER tools that assign the handlers (`errorHandlersActive`, debug warning at launch), never throw/block, treat the same object or fingerprint (first line of the reason + top frames) seen twice within a second as ONE (silent, not counted), then an equal error at most once in 30 s / 10 per 60 s on a monotonic clock, skip `silent` errors, read nothing but exception and stack from `FlutterErrorDetails` (a `FlutterError` contributes its summary), and obey `detect.crash` false. Default `reportAsCrash` is FALSE (error reports): Dart errors never end the app, RN files only fatal errors as crashes, crash reports count against crash-free sessions and replace iOS's single stored crash report; true is an opt-in (9.x reported FlutterError.onError as unhandled). No severity/skipFrames: neither SDK takes them for exceptions. Symbols are uploaded with the 9.x `scripts/symbols.py` protocol (bugsee-cli has no Flutter support yet): documented, not reimplemented; `scripts/verify_symbolization.dart` and `scripts/verify_worker_contract.py` (local, worker checkout) are the offline checks. Device test: `example/integration_test/exceptions_test.dart` (iOS files nothing on a simulator).

## Report files (attachments, screenshots, `createReport`)

Report files (`ReportOps.java` + `ReportFileFlow.java` + `CreatedReports.java`, `BGSFlutterReportFiles` + `BGSFlutterReportFileFlow` + `BGSFlutterCreatedReports` + `BGSFlutterCreatedReportOps`, Dart `lib/src/report/{attachments,created_report,report_proxy}.dart`, `doc/attachments.md`): PATH-FIRST (a path crosses, never a stream or bitmap; bytes only up to 1 MiB). File work runs on a one-thread worker, NEVER the platform thread, and a handler report is CLAIMED (`acquire`/lease) before it is queued so the SDK's completion waits for the claim instead of racing it; nothing blocks (the drift guard greps). Codes (`not-live`, `file-not-found`, ...), limits, the name/MIME/path rules and the MIME regex are repeated in Dart/Java/ObjC and compared by `test/report_attachments_drift_test.dart`; the SDKs' own attachment caps are EXTRACTED into `test/fixtures/report_enums.json` (`scripts/extract_report_enums.dart`, now also `--android-report/--ios-report/--ios-attachment`). A refused add never consumes the source (a refused `move` neither). ANDROID 7.4.2 DOES NOT RE-CHECK that the report still takes attachments after importing the file (`IssueReport.java:292-299` checks before `importFile`, `:361-372` registers without looking again), so a copy that outlives the SDK's handler timer lands as an orphan: the wrapper never asks the SDK to rename (a move is copy + delete of the source after the add is known to have landed), asks the lease whether the handler's window closed (`Lease.windowClosed`) before AND after the add, undoes a late add (`Attachment.deleteFile`) and answers `rejected` with the source intact; a 20 MiB per-file soft limit bounds the copy; iOS re-checks under its lock itself. Created reports are released per ENGINE (`reserve(owner)`/`clearOwner`: a second engine's start must not destroy the first one's), at most 6 starts a minute (the SDKs cannot cancel a created report), upload has a 45 s deadline (`upload-timeout`), and created-report work has its own worker so a slow handler copy never blocks it. `createReport`: one at a time, stamped reservation, deadline at each stage (45 s SDK, time to live), released on hot restart; iOS's created report is the legacy `BugseeExtendedReport` (3 attachments x 3 MiB, no id/flag): refused here, not dropped at upload. The integration test needs the stand-in API `example/integration_test/support/mock_api.py`.

## Feedback package

Feedback package (`packages/bugsee_flutter_feedback`, doc `packages/bugsee_flutter_feedback/doc/feedback.md`): the in-app chat is a SEPARATE package (D4), a member of the repo's pub workspace (root `pubspec.yaml` `workspace:` with `example`), released in lock-step with the core (same version; constraint `>=<core> <next minor>`, never exact: pub warns; never a path dependency or an override: unpublishable). The core must never mention it (`test/feedback_package_drift_test.dart` greps lib, android, ios, the core bridge for `BugseeFeedback`/`SwiftUI`); its bridge is its OWN Pigeon definition (`packages/bugsee_flutter_feedback/pigeons`, `dart scripts/generate_pigeon.dart --package packages/bugsee_flutter_feedback`), never widen the core's. Native pins are LITERALS in its `build.gradle` / `Package.swift` (no `native-versions.json` next to a published copy), compared by that test. It adds NO Android provider (the SDK's own `BugseeFeedbackInitProvider`, or the Gradle plugin's injected `registerFeedbackExtension()`, registers the module; our call is a safety net) and on iOS it registers `BugseeFeedback` from its own `+load` registrar, referenced by the Swift plugin class, because the add-on's `+load` shim can be dead-stripped from a static link. Publish order: the core first. The sibling is dry-run/published ONLY through `scripts/publish_feedback.sh` (a copy of the TRACKED files without `.git`; a real publish refuses a dirty tree; both archives go through `scripts/check_pub_archive.sh`). Listener slot: one SDK slot per process, so the wrapper hands the SDK ONE fan-out listener (Android `FeedbackOps.FANOUT`, iOS `BGSFlutterFeedbackFanout` + `BGSFlutterFeedbackAdapterSlot`, which tells the add-on once and never with nil: its `setListener` changes are unordered tasks): the root `.pubignore` drops `/packages/` and pub applies every ancestor `.pubignore`, so it cannot be published from its own directory in this repo. iOS tests: `packages/bugsee_flutter_feedback/ios/feedback_wrapper_tests` (same arrangement as `ios/wrapper_tests`); Android: `./gradlew :bugsee_flutter_feedback:testDebugUnitTest` from `example/android`.

## Device verification

Device verification (`scripts/device/`, the app `example/lib/verify_main.dart`, results and evidence `doc/verification.md`): workbook Part 9 as a harness, NOT in CI. Its guards are the default and must stay so: the SDK banner's version AND build (`android.sdkBuild`, `ios.sdkBuild` in `native-versions.json`), the artefact set (NDK artefact, Gradle plugin alone at the pin, four `libbugsee*.so`, provider kept at `initOrder` 200; iOS SwiftPM tag AND revision), launched, staged preconditions read back, the death of signal 11 proven (logcat plus exit info, launchd on iOS), a positive control next to every absence.
